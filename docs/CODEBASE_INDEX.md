# VARS KB Editor — Codebase Index

Generated by a full read-through of the repository (2026-09-06), drift-checked and updated 2026-11-06. React 19 + Vite 8 + MUI 9 knowledge-base editor for MBARI's VARS taxonomy/annotation services. ~690 source files, ~115 test files. Base path `/kbeditor/`, Yarn 4, Vitest + jsdom.

This is a navigation map, not API documentation. Use it to locate where things live before reading code.

## Entry chain

`index.html` → `src/main.jsx` → `src/components/App.jsx` (theme, router basename `/kbeditor/`, `Whoops` error boundary) → `ConfigProvider` → `UserProvider` → `AuthRoute` (gates on auth + valid config, else `startup/StartUp`) → `KBContainer` → `KnowledgeBase`.

`src/version.js` is auto-generated by `scripts/version/tag.js` via `vite-plugins/version-plugin.js` (date-based `YYYY.MM.DD-HHMM` + git metadata; gitignored).

## Provider stack (KBContainer)

```
AppModalProvider → RefreshContext (value built in KBContainer; refresh() flushes prefs, remounts subtree via key)
  → TaxonomyProvider(key=refreshKey) → PreferencesProvider → SelectedProvider
    → UsersProvider → PanelDataProvider → ConceptModalProvider → ConceptProvider → KnowledgeBase
```

Panel-level providers mount inside their panels: `HistoryProvider`, `RealizationsProvider`, `ReferencesProvider`, `TemplatesProvider`, `UsersProvider` (also mounted globally). `KnowledgeBase.jsx` wraps `NavBar` + `Panels` in the shared `PanelModalProvider` (from `@/contexts/panel/modal`; moved up from `Panels.jsx` in the 2026-10-31 modal DRY rework) and keeps inactive panels mounted-but-hidden.

## src/contexts/ — state layer

Only one reducer in the entire app: `conceptStateReducer` (`panels/concepts/staged/edit/conceptStateReducer.js`). Everything else is `useState`/`useRef` + extracted hooks.

Context/provider pairing exceptions (contexts with no dedicated provider file):
- `RefreshContext` — value built inline in `KBContainer.jsx` (refresh key + flush-preferences closure live there).
- `ConceptStagedContext` — value built inline in `ConceptProvider.jsx`; its keys (`stagedState`, `modifyConcept`, `confirmReset`) derive entirely from state `ConceptProvider` owns. A separate provider would be a pass-through, and moving the staged state out would create a circular dependency (`useModifyConcept` needs `initialState`; `ConceptProvider` effects need `stagedState`).
- `SelectedSettingsContext` — value built inline in `SelectedProvider.jsx`; its keys (`settings`, `getSettings`, `setSettings`, `updateSettings`) derive from the `useSettings` state `SelectedProvider` owns. Split out so filter keystrokes don't re-render all selection consumers.
- `ConceptModalDataContext` / `ConceptModalProcessingContext` — values built inline in `ConceptModalProvider.jsx` alongside the ops `ConceptModalContext` (which is stabilized via `onCloseRef`/`modalDataRef`/`processingRef` so its identity never changes after mount).
- `createPanelModalProvider` — inverse case: ONE provider emitting TWO contexts (Data + Operations).

| Provider | Role |
|---|---|
| `config/ConfigProvider` | Endpoint discovery, service-token manager, app preferences (`mediaBaseURL`, `phylogenyRoot`, `dsgConceptUrl`), `apiFns` (`apiPayload`/`apiPaginated`/`apiResult`/`apiRaw`) |
| `user/UserProvider` | Session lifecycle, token refresh (1h window), unsaved-changes guard (`guardedAction`), `savePreferencesRef` flush slot. Internals in `user/lib/` (`useProcessAuth`, `useRefreshUser`, `useLogout`, `useInvalidAuth`) |
| `taxonomy/TaxonomyProvider` | Normalized taxonomy graph, lazy hydration, integrity checks (`useTaxonomyIntegrity`), `conceptEditsRefresh` post-edit reconciliation; all mutations serialized through `enqueueTaxonomyMutation` (latest-state queue) so concurrent loaders can't clobber each other |
| `preferences/PreferencesProvider` | Server prefs bridge: `useInitPrefs` (normalize stored history), `usePrefsTimer` (autosave), `useSavePrefs` (dirty-flag flush) |
| `selected/SelectedProvider` | Current concept/panel (history stacks over `lib/local/state/historyState`), `updateSelected`. Provides two contexts: `SelectedContext` (selection, low-frequency) and `SelectedSettingsContext` (per-panel `settings`/filters via `useSettings`, filter-frequency: `settings`, `getSettings`, `setSettings`, `updateSettings`) |
| `panel/data/PanelDataProvider` | Central caches: references, realizations, templates, pending history, `explicitConcepts`; `refreshData(type)` |
| `panels/concepts/ConceptProvider` | The editing state machine: `concept` + immutable `initialState` + `stagedState` reducer; `staged/edit/` (reducer, `useModifyConcept` reset-confirm flow, `stateUpdates`), `staged/save/` (`useSaveStaged` orchestrator, 8 `submitter/*` API modules, `applier/*` result mutators, `applyRenameSideEffects`), `pending/` (`useConceptPending`, `useConceptUpdatePending`, `approve/*` + `reject/*` pure mutators). Provides two contexts: `ConceptContext` (low-frequency: concept, isEditing, initialState, pending) and `ConceptStagedContext` (keystroke-frequency: `stagedState`, `modifyConcept`, `confirmReset`) — the split keeps per-keystroke dispatches from re-rendering all concept consumers |
| `panels/history/` | HistoryProvider: 3 history types (pending/approved/concept) × extents (solo/children/descendants); approved is server-paginated, others client-paginated |
| `panels/realizations/` | RealizationsProvider: filtered view over PanelData cache + edit/delete CRUD (`useModifyRealizations`), pending-action row gating, panel modal system (`modal.js` via `createPanelModalProvider`) |
| `panels/references/` | ReferencesProvider: CRUD + concept/extent filters (`useModifyReferences` writes to shared cache) |
| `panels/templates/` | TemplatesProvider: CRUD + filters + `byAvailable` ancestor widening |
| `panels/users/` | UsersProvider: admin-only user CRUD (also mounted globally in KBContainer) |
| `common/createPanelModalProvider` | Factory stamping two-context modal systems (Data + Operations); instantiated once as the shared `panel/modal/` provider (used by History) and per-panel in `panels/{users,templates,references,realizations}/modal.js` |

Three modal tiers: app-level (`AppModalProvider`), concept-panel (`ConceptModalProvider`, hand-rolled — provides three contexts: `ConceptModalContext` ops (stable via refs), `ConceptModalDataContext` (`modal`/`modalData`), `ConceptModalProcessingContext` (`processing`/`processingMessage`)), generic panel (factory-generated Data + Operations via `createPanelModalProvider`; shared instance mounted in `KnowledgeBase.jsx`, per-panel instances inside each panel provider, all rendering through the shared `PanelModal.jsx`/`ModalShell.jsx`).

## src/components/ — UI tree

- **Shell**: `App.jsx`, `Whoops.jsx`, `auth/AuthRoute.jsx`, `startup/` (ConfigForm → LoginForm flow), `kb/KBContainer.jsx`, `KnowledgeBase.jsx`, `Panels.jsx` + `panels/modules.js` (registry of nine panels as dynamic-import chunk loaders: Concepts, Templates, Realizations, References, Embargoes, History, Notes, Users, AboutHelp; `Panel.jsx` loads chunks via explicit `LazyPanel` with a module-level cache — deliberately not React.lazy/Suspense, whose fallback can stick in the hidden keep-alive panels — and keeps inactive panels mounted-but-hidden after first activation)
- **Nav**: `kb/nav/NavBar.jsx` (PanelLinks, Users hidden for non-admin), `UserActions`, `nav/appInfo/` (editable app-preference settings), `kb/browserBack/` (popstate → logout-confirm modal)
- **Concepts panel** (deepest): sidebar (`ConceptSelect` + `ConceptsTree` — MUI `RichTreeView` with custom item slots, lazy hydration, arrow-key nav (Alt+click on selected item = expand all descendants: one `phylogeny/down` call commits structure immediately, then per-concept media for tree icons fills in asynchronously, breadth-first), auto-expand/scroll in `sidebar/tree/lib/`) | draggable divider | detail view (`concept/detail/`: name/author/rank/aliases/media-with-swiper/realizations/references/templates + generic paginated `properties/` framework) and editing UI (`concept/change/staged/*` per-field staged editors + `change/pending/*` read-only approval mirror)
- **Table panels** (History, Realizations, References, Templates, Users): all compose `common/panel/usePanelFactory` + `PanelDataGrid` (MUI DataGrid), per-panel `use*Columns.jsx`, `*Pagination.jsx`, `use*Export.js` CSV hooks, `form/` + modal button hooks
- **Common**: `concept/` picker family (`ConceptSelect`, `ToConceptSelect`, `ConceptExtent`, `RelatedDataCounts`), `factory/` modal primitives, `panel/` layout framework (incl. `EmptyPanel`, used by the Notes/Embargoes placeholders), `tooltip/` (`KBTooltip`, `KBTooltipTarget`, `KBTooltipFormControlLabel`)
- **Modal framework**: `modal/AppModal.jsx`, `ConceptModal.jsx`, `PanelModal.jsx`, `KbLoading.jsx`, shared `actions/` alerts

## src/config/ — bundled UI strings and user-tunable constants (JSON)

Mostly pure label/tooltip/alert-text JSON (no field/column/form specs), consumed via `src/lib/config` wrappers as `CONFIG.PANELS.*`. Per-panel dirs: `concepts/` (rich: aliases, rank, realizations, structure + `modals/{alias,media,realization,structure}/*`), `history/`, `references/`, `templates/`, `users/` (+ their `modals/`), minimal `embargoes|notes|abouthelp`. Root: `appInfo`, `button`, `concept`, `export`, `security` (encryption params), `processing`, `whoops`. The `constants/` dir holds user-tunable numeric/behavioral values (currently `pagination.json` → `PAGINATION`), wrapped by `src/lib/config/constants/` and registered as `CONFIG.CONSTANTS.*`.

## Key request flows

### API call
`api/*.js` → `services/<svc>/methods.js` → `request.js` (service token for reads, oni-user token for attributed mutations, one 401-retry after refresh) → fetch. Contexts unwrap via `ConfigContext.apiFns`. Result convention: `{payload}` / `{error, status}` / `{error, result}`.

### Concept save
`StagedActions` → `useSaveStaged` → `submitStaged` (8 field submitters in `staged/save/submitter/`, `Promise.all`) → `applyRenameSideEffects` (if renamed: related-data reassignment, prefs history rewrite, template filter rewrite) → refetch + `normalizeConcept` → `applyUpdateResults` (per-field `applier/*`) → refresh pending history → `conceptEditsRefresh` (taxonomy reconciliation) → `setConcept` → exit editing.

### Pending approval
Context hooks (`useConceptUpdatePending` / `useHistoryUpdatePending`) → `lib/concept/pending/processPendingApproval` → `updatePendingItem` PUTs → optimistic clone/mutate via `panels/concepts/pending/approve/*` or `reject/*` (pure mutators dispatched by `HISTORY_FIELD`) → `conceptEditsRefresh`.
