## Code style preferences
- No defensive programming — this is a hard rule, not a preference. Do not add guards, fallbacks, type-checks, or null-checks for conditions that should not occur; let errors surface at their source. Defensive code shunts failures away from the root cause, rarely offers a meaningful recovery path, and every guard for an impossible state costs a future maintainer a wasted thought cycle ("when is this not an Array? what should happen then?"). Only handle an error where there is a real "what should happen next" answer. When a value has exactly two real states (e.g. absent vs. Array), use the precise construct for those states (`?.`) rather than a type check (`Array.isArray`) that implies states which cannot occur.
- Minimal comments. Code must be self-explanatory through naming and structure. Do not add explanatory block comments, rationale notes, or "what/why" narration in source files; that material belongs in docs (`AGENTS.md`, `docs/`) and commit messages.

## High-level architecture
### Runtime entry and route gating
- `src/main.jsx` mounts `App`.
- `src/components/App.jsx` sets MUI theme, router basename (`/kbeditor/`), and provider order:
  - `ConfigProvider` -> `UserProvider` -> `AuthRoute` -> `KBContainer`.
- `AuthRoute` only renders KB routes when both conditions are met:
  - user is authenticated (`UserContext`)
  - service config is valid (`ConfigContext`)
  Otherwise it renders startup/login flow (`StartUp`).

### Configuration and API wiring
- `ConfigProvider` is the integration point for backend endpoint discovery:
  - fetches `<config-url>/endpoints` via `getEndpoints`
  - builds service lookup for `oni` and `annosaurus`
  - exposes `apiFns` helpers (`apiPayload`, `apiPaginated`, `apiResult`, `apiRaw`) used by the rest of the app.
- API modules in `src/lib/api/` are thin per-domain wrappers; transport is centralized in:
  - `src/lib/services/request.js` (token attach, exactly one 401-retry after refresh)
  - `src/lib/services/oni/methods.js`
  - `src/lib/services/annosaurus/methods.js`

### Provider stack inside the KB app
- `KBContainer` composes the main runtime providers in this order:
  - `AppModalProvider`
  - `RefreshContext` (global refresh trigger + preference flush)
  - `TaxonomyProvider` (taxonomy graph + lazy loading)
  - `PreferencesProvider` (user preference autosave)
  - `SelectedProvider` (selected panel/concept and settings)
  - `UsersProvider`
  - `PanelDataProvider` (references/templates/pending-history caches)
  - `ConceptModalProvider`
  - `ConceptProvider` (concept editing state machine)
- `KnowledgeBase` renders navbar + panel area and mounts modal/loading overlays, including the shared `PanelModalProvider`.

### Panel system
- Panel registration is centralized in `src/components/kb/panels/modules.js`; each entry is a `load: () => import(...)` chunk loader.
- `Panel.jsx` loads panel chunks via explicit dynamic import with a module-level cache (`LazyPanel`), not `React.lazy`/`Suspense` — Suspense boundaries inside the keep-alive hidden (`display:none`) panels can stick on their fallback when a switch happens mid-load.
- Panels mount lazily (active panel first, others on first activation) and are hidden, not destroyed, once mounted.
- This preserves per-panel UI state across panel switches while keeping panel code out of the startup chunk.

### Taxonomy and concept editing model
- `TaxonomyProvider` maintains normalized taxonomy state (`conceptMap`, `aliasMap`, `names`, `ranks`, `rootName`) and provides lazy loaders:
  - initial root load
  - incremental concept/descendant hydration for tree navigation.
- Descendant (expand-all) loads commit the phylogeny structure immediately; per-concept media for tree icons then fills in asynchronously via `loadConceptMediaIncremental`, breadth-first (children before grandchildren, matching how the user reads the tree). Media-fill failures never reach the error boundary; unset `media` simply renders no icon.
- All taxonomy mutations — concept/children/descendants loads, `conceptEditsRefresh`, background media flushes — are serialized through `enqueueTaxonomyMutation` in `TaxonomyProvider`: each mutation builds on the latest committed taxonomy (`taxonomyRef`) rather than a render-scope snapshot, so concurrent loaders (e.g. an opt-click descendants expand racing the selection-triggered concept load) cannot clobber each other's commits.
- Taxonomy model logic lives in `src/lib/model/taxonomy.js` (tree building, alias mapping, refresh/remove logic).
- `ConceptProvider` owns staged concept editing:
  - reducer-driven staged state (`conceptStateReducer`)
  - unsaved-change guards via `UserContext`
  - pending-history integration for approval/rejection workflows
  - concept-path loading used to expand/scroll the tree to current concept.

### Selection and preferences coupling
- `SelectedProvider` exposes concept/panel selection APIs and syncs through `PreferencesContext`.
- `PreferencesProvider` persists panel/concept/settings selections to user preferences with dirty flags + autosave timer, and exposes a flush function via `savePreferencesRef` for safe refresh/logout transitions.

### State management conventions
- Only one reducer exists in the app: `conceptStateReducer` (`src/contexts/panels/concepts/staged/edit/conceptStateReducer.js`). All other state is `useState`/`useRef` + extracted hooks.
- The reducer dispatches `CONCEPT_STATE` actions (`src/lib/constants/conceptState.js`) to pure per-field modules in `src/lib/concept/state/` (`initialState` / `isModified` / `stateUpdates` contract).
- Concept editing uses two contexts: `ConceptContext` (low-frequency keys: concept, isEditing, initialState, pending, ...) and `ConceptStagedContext` (keystroke-frequency keys: `stagedState`, `modifyConcept`, `confirmReset`). The split exists so per-keystroke dispatches only re-render staged-editing consumers; when adding editing UI, consume staged keys from `ConceptStagedContext`.
- Selection uses two contexts: `SelectedContext` (low-frequency keys: concepts, panels, getSelected, updateSelected, isLoading) and `SelectedSettingsContext` (filter-frequency keys: `settings`, `getSettings`, `setSettings`, `updateSettings`). The split exists so filter keystrokes in one panel do not re-render every selection consumer (navbar, tree, other panels); consume settings keys from `SelectedSettingsContext`.
- `ConceptStagedContext` and `SelectedSettingsContext` deliberately have no parallel provider files: their values derive entirely from state owned by `ConceptProvider`/`SelectedProvider` respectively, which provide them inline (same precedent as `RefreshContext`, whose value is built in `KBContainer`). A separate provider would be a pass-through, and moving the staged state out of `ConceptProvider` would create a circular dependency (`useModifyConcept` needs `initialState`; `ConceptProvider` effects need `stagedState`). `ConceptModalDataContext`/`ConceptModalProcessingContext` are likewise provided inline by `ConceptModalProvider`.
- API result convention: `{payload}` / `{error, status}`. Unwrap via `apiFns` from `ConfigContext`, not raw fetch.
- Saving staged edits runs through `useSaveStaged` -> per-field submitters (`staged/save/submitter/*`) -> appliers (`staged/save/applier/*`) -> `conceptEditsRefresh` in `TaxonomyProvider`.
- Pending-history approve/reject mutators live in `src/contexts/panels/concepts/pending/{approve,reject}/` and are orchestrated by `src/lib/concept/pending/processPendingApproval.js`.

### Modal architecture (three tiers)
- App level: `AppModalProvider` + `src/components/modal/AppModal.jsx` (errors, logout confirm, export complete, app info).
- Concept panel: `ConceptModalProvider` (hand-rolled) + `ConceptModal.jsx` (staged/pending editing modals). It provides three contexts: `ConceptModalContext` (ops, stable identity: closeModal, setModal, setModalData, beginProcessing, withProcessing), `ConceptModalDataContext` (`modal`, `modalData`), and `ConceptModalProcessingContext` (`processing`, `processingMessage`). Ops is stabilized via refs (onCloseRef/modalDataRef/processingRef in closeModal), so modal triggers never re-render from modal activity.
- Other panels: factory-generated via `src/contexts/common/createPanelModalProvider.jsx` (two contexts per panel: Data + Operations) + shared `PanelModal.jsx`/`ModalShell.jsx`. A shared instance (`src/contexts/panel/modal/`) is mounted in `KnowledgeBase.jsx`; per-panel instances (`src/contexts/panels/<name>/modal.js`) mount inside each panel provider.

### Table panel composition
- Table panels (History, Realizations, References, Templates, Users) compose `usePanelFactory` + `PanelDataGrid` (MUI DataGrid wrapper) from `src/components/common/panel/`.
- Per-panel conventions: `use*Columns.jsx` for columns, `*Pagination.jsx` for paging, `use*Export.js` for CSV export.
- UI strings come from `src/config/**.json` via the `CONFIG` registry in `src/lib/config/` — do not hardcode labels in components.

## Test layout
- Tests use Vitest + jsdom (`vite.config.js`, `test/setup.js`).
- Test organization mirrors app domains:
  - `test/components/...`
  - `test/contexts/...`
  - `test/lib/...`
- Many tests are integration-heavy around providers and panel behavior; when changing provider contracts, run the related context and panel test folders, not only leaf unit tests.

## UI conventions
### KBTooltip
- Wrap the actual interactive target with `KBTooltip` (button, icon button, switch label, toggle, etc.), not only nested text.
- For potentially disabled targets, render a wrapper element (`span`/`Box component='span'`) inside `KBTooltip` so hover still works.
- Prefer shared wrappers in `src/components/common/tooltip/` over ad-hoc inline patterns:
  - `TooltipTarget` for generic interactive children.
  - `TooltipFormControlLabel` for labeled checkbox/switch controls.
